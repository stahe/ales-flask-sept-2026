    1.1. El papel de Flask en una aplicación web

    Una aplicación web suele construirse en capas, y cada capa se comunica solo con las capas vecinas:

    • la capa web recibe las solicitudes HTTP del navegador y le devuelve páginas HTML. Es la capa que [Flask] nos ayuda a escribir;
    • la capa de negocio contiene las reglas de negocio de la aplicación (por ejemplo, “un paciente solo puede tener una cita próxima”). No sabe nada de la web: podría servir igualmente a una aplicación de línea de comandos;
    • la capa de acceso a datos (capa [DAO], por [Data Access Object]) lee y escribe en la base de datos. Usaremos [SQLAlchemy], un ORM ([Object Relational Mapper]) que asocia las filas de las tablas con objetos [Python].

    La propia capa web sigue el modelo [MVC] ([Model – View – Controller]):

    • el controlador (C) es un conjunto de funciones [Python], llamadas acciones, cada una de las cuales procesa un tipo de solicitud (por ejemplo, [GET /schedule]). Una acción lee los parámetros de la solicitud, invoca la capa de negocio y luego elige la vista que se mostrará;
    • el modelo (M) es el conjunto de datos que la acción pasa a la vista;
    • la vista (V) es un archivo [Jinja2] (extensión [.html]): una página HTML que contiene expresiones [{{ ... }}] e instrucciones [{% ... %}] ([{% if %}], [{% for %}]...), que el motor [Jinja2] reemplaza con los datos del modelo.

    Una nota sobre la terminología, para evitar confusiones: la documentación de [Flask] llama a la función que procesa una solicitud “función de vista” (“view function”) y al archivo [Jinja2] “plantilla” (“template”). Este documento usa la terminología del modelo [MVC], así como la de los cursos de [Spring MVC] y [ASP.NET Core MVC] : la función que procesa una solicitud es una acción, el archivo [Jinja2] que genera la página es una vista, y el término “plantilla” designa la vista común de la que heredan las demás páginas (capítulo 4).

    El procesamiento de una solicitud sigue los pasos numerados del diagrama:

    • 1: El navegador envía una solicitud, por ejemplo HTTP o [GET /schedule?doctorId=1&day=2026-09-26];
    • 2: El servidor web recibe la solicitud y se la pasa a la aplicación [Flask]. Durante el desarrollo, este servidor es [Werkzeug], la biblioteca sobre la que se construye [Flask] ; en producción, será un servidor como [Waitress] o [Gunicorn]. [Werkzeug] compara la ruta solicitada con las rutas de la aplicación y selecciona la acción encargada de manejar esta solicitud: es el enrutamiento. Antes de llegar a la acción, la solicitud puede pasar aún por funciones que se ejecutan para todas las solicitudes ([before_request]), que exploraremos en los capítulos siguientes;
    • 3: La acción pide a la capa de negocio los datos que necesita; si es necesario, la capa de negocio contacta a la capa [DAO], que consulta la base de datos [MySQL] mediante SQL;
    • 4: La acción construye el modelo M de la vista e indica al motor [Jinja2] que genere la página (función [render_template]);
    • 5: La página HTML generada por la vista es la respuesta de la acción, que [Flask] devuelve al navegador.

    [Flask] es uno de los dos frameworks web más utilizados en el mundo [Python], junto con [Django]. Es libre y de código abierto, y funciona en cualquier lugar donde funcione [Python] ([Windows], [Linux], [macOS]). Es un microframework: su núcleo es deliberadamente pequeño (enrutamiento, solicitudes y respuestas, sesiones, vistas [Jinja2]), y todo lo demás (validación de formularios, acceso a bases de datos, autenticación, etc.) lo resuelven bibliotecas elegidas por el desarrollador. Mientras que [Spring Boot] configura por sí solo un conjunto coherente de componentes, [Flask] permite al desarrollador ensamblar los suyos: la aplicación es más transparente y se puede ver todo lo que ocurre en su interior. Esto es, de hecho, lo que lo convierte en una buena herramienta para aprender: casi nada está oculto. [Flask] puede crear servidores que devuelven JSON a un cliente [JavaScript] ([Angular], [React], [Flutter]...) igual que aplicaciones web tradicionales, en las que el servidor genera las páginas HTML y el navegador se limita a mostrarlas. Este documento examina este segundo caso de uso. Dos conceptos de [Python] se repiten en cada página: los decoradores ([@app.get("/")], [@app.before_request]...), que asocian una función con un rol, y el paso explícito de los objetos que necesita cada función, mientras que [Spring] los inyecta automáticamente.

    1.2. Herramientas utilizadas

    Los ejemplos se escribieron y probaron con las siguientes herramientas (su instalación se describe en el apéndice):

    • [Python] 3.13 (sirve cualquier versión 3.12 o posterior). El instalador de [Python] también proporciona la herramienta [pip], que descarga e instala las bibliotecas, y el módulo [venv], que crea entornos virtuales (más adelante veremos qué son);

    app.jinja_env.trim_blocks = True
    app.jinja_env.lstrip_blocks = True
    # un blueprint sin rutas, que solo sirve archivos estáticos: la
    # carpeta BOOTSTRAP, bajo la URL /bootstrap/...
    app.register_blueprint(Blueprint("bootstrap", __name__, static_folder=BOOTSTRAP,
                                     static_url_path="/bootstrap"))
    app.register_blueprint(pages)
    • Línea 11: la ruta a la carpeta [common/bootstrap]. [__file__] es la ruta del archivo que se está ejecutando ([app.py]); [Path(...).resolve()] la convierte en una ruta absoluta; [.parent] designa la carpeta que lo contiene ([15-layout]), y [.parent.parent] designa la carpeta padre ([examples]). El operador [/] de un objeto [Path] agrega un elemento a la ruta, con el separador correcto ([\] en [Windows], [/] en los demás). Así, la ruta no depende de la carpeta actual: el ejemplo encuentra [Bootstrap] sin importar desde dónde se inicie;
    • líneas 20 y 21: un blueprint es un grupo de rutas almacenado en la aplicación (vea el ejemplo 02). Este blueprint no tiene rutas: sirve únicamente para publicar la carpeta [common/bootstrap] (parámetro [static_folder]) bajo la URL [/bootstrap] (parámetro [static_url_path]). Una página puede usar así la hoja de estilo [/bootstrap/css/bootstrap.min.css].

    Las demás líneas de este archivo se explicarán en el ejemplo 15.
