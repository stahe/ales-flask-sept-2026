    8. Autenticación y autorización

    Para cada solicitud se plantean dos preguntas distintas:

    • ¿Quién es el usuario? Esto es la autenticación: el usuario se ha identificado con un nombre de usuario y una contraseña, y cada solicitud posterior debe demostrar que proviene de él;
    • ¿Tiene permiso para acceder a esta página? Esto es la autorización: en el caso de estudio, solo un usuario con el rol ADMIN administra los médicos y los clientes.

    Dado que el servidor no tiene estado (véase el capítulo sobre los ámbitos), la prueba de identidad debe incluirse en cada solicitud. Se usa un token llamado JWT (*JSON Web Token*): después del inicio de sesión, el servidor genera un token que contiene la identidad del usuario y lo firma con una clave secreta. El token se almacena en una cookie; el navegador lo reenvía con cada solicitud; el servidor verifica la firma. El usuario puede leer su token, pero no puede modificarlo: cualquier modificación invalida la firma. Es el mismo principio que el de la sesión de [Flask] (ejemplo 20), pero con un formato estandarizado (RFC 7519) que entienden todos los lenguajes de programación y con una fecha de expiración incorporada en el token.

    [Flask] no tiene un mecanismo de seguridad integrado, a diferencia de [Spring] ([Spring Security]) o de [ASP.NET Core]. Existen extensiones ([Flask-Login], [Flask-JWT-Extended]...), pero el mecanismo es lo bastante simple como para escribirlo a mano con las herramientas de los capítulos anteriores, lo que tiene la ventaja de hacerlo transparente:

    • la autenticación está a cargo de una función [before_request] (capítulo anterior), que recupera el token de la cookie, lo verifica y almacena el usuario autenticado en [g], el objeto de la solicitud;
    • la autorización está a cargo de decoradores aplicados a las acciones ([@login_required], [@role_required("ADMIN")]), construidos como el decorador [@with_language] del ejemplo 12.

    Se usan dos bibliotecas, instaladas con el archivo [requirements.txt] de los ejemplos: [PyJWT], que genera y verifica tokens, y [bcrypt], que calcula el hash de las contraseñas.

from pathlib import Path

from flask import Blueprint, Flask

from auth import security
from auth.service import AuthService
from auth.users import UsersService
from controllers.auth import auth
from controllers.profile import profile

BOOTSTRAP = Path(__file__).resolve().parent.parent / "common" / "bootstrap"


def create_app():
    app = Flask(__name__)
    app.jinja_env.trim_blocks = True
    app.jinja_env.lstrip_blocks = True
    # la configuración: el archivo config.py, luego las variables de entorno
    # que empiezan con FLASK_ (FLASK_JWT_SECRET reemplaza a JWT_SECRET)
    app.config.from_pyfile("config.py")
    app.config.from_prefixed_env()
    # los servicios de autenticación
    users = UsersService()
    app.extensions["auth"] = AuthService(users, app.config["JWT_SECRET"],
                                         app.config["JWT_DURATION_MINUTES"])
    app.register_blueprint(Blueprint("bootstrap", __name__, static_folder=BOOTSTRAP,
                                     static_url_path="/bootstrap"))
    app.register_blueprint(auth)
    app.register_blueprint(profile)
    # el usuario de cada solicitud, leído del token de la cookie
    security.register(app)
    return app


if __name__ == "__main__":
    create_app().run(port=5000, debug=True)

from dataclasses import dataclass

import bcrypt


@dataclass(frozen=True)
class User:
    login: str
    name: str
    role: str
    password_hash: bytes


# el hash de una contraseña: bcrypt, con un costo de 10 (2^10 rondas);
# gensalt genera una "sal" aleatoria, que se almacena en el propio hash
def hash_password(password: str) -> bytes:
    return bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=10))


class UsersService:

    def __init__(self):
        # NUNCA guardamos una contraseña, solo su hash
        self._users = {u.login: u for u in (
            User("marie", "Marie Pélissier", "USER", hash_password("marie")),
            User("admin", "Administrator", "ADMIN", hash_password("admin")),
        )}

    def find(self, login: str) -> User | None:
        return self._users.get(login)
    • líneas 9–13: un usuario: su nombre de usuario, nombre, rol y el hash de su contraseña. Un servidor nunca almacena una contraseña, ni siquiera cifrada: si se robara la base de datos, también se robarían las contraseñas (y mucha gente usa la misma contraseña en todas partes). Almacena el resultado de una función hash, una función unidireccional: se puede calcular el hash de una contraseña, pero no se puede recuperar una contraseña a partir de su hash. Para verificar una contraseña ingresada, se calcula su hash y se compara con el que está almacenado;
    • líneas 18–19: cálculo del hash con el algoritmo [bcrypt], diseñado para contraseñas. Tiene dos características distintivas. Es intencionalmente lento, con una lentitud ajustable (el parámetro [rounds], o costo: 2^10 ciclos de cálculo): unas decenas de milisegundos, imperceptibles para un usuario, pero que hacen muy costoso para un atacante probar miles de millones de contraseñas. Usa un salt: [gensalt] genera aleatoriamente un salt, lo mezcla con la contraseña antes de calcular el hash y lo almacena dentro del propio hash; así, dos usuarios con la misma contraseña tendrán hashes diferentes. [bcrypt] opera con bytes: [encode()] convierte la cadena en bytes ([UTF-8]). Solo considera los primeros 72 bytes de una contraseña, y la versión 5 de la biblioteca rechaza las contraseñas más largas (el caso de estudio lo tiene en cuenta);
    • líneas 26–28: dos usuarios de prueba, almacenados en memoria y organizados en un diccionario construido por comprensión ([{key: value for ...}]). El ejemplo 28 y el caso de estudio los almacenarán en una base de datos.

    # auth/service.py: la verificación de las contraseñas y los tokens JWT
from datetime import datetime, timedelta, timezone

import bcrypt
import jwt
from flask import current_app

from auth.users import User, UsersService

# el nombre de la cookie que transporta el token
COOKIE = "token"


class AuthService:

    def __init__(self, users: UsersService, secret: str, duration_minutes: int):
        self._users = users
        self._secret = secret
        self.duration = timedelta(minutes=duration_minutes)

    # el usuario, o None si el login es desconocido o la contraseña es incorrecta.
    # checkpw calcula el hash de la contraseña ingresada con la sal del hash almacenado,
    # y luego compara los dos resultados
    def validate(self, login: str | None, password: str | None) -> User | None:
        if not login or password is None:
            return None
        user = self._users.find(login)
        if user is None or not bcrypt.checkpw(password.encode(),
                                              user.password_hash):
            return None
        return user

    # el token JWT del usuario, firmado con la clave secreta (HMAC-SHA256)
    def create_token(self, user: User) -> str:
        now = datetime.now(timezone.utc)
        # el contenido del token: los "claims" (afirmaciones sobre el usuario)
        claims = {
            "sub": user.login,
            "name": user.name,
            "role": user.role,
            "iat": now,
            "exp": now + self.duration,
        }
        return jwt.encode(claims, self._secret, algorithm="HS256")

    # los claims de un token cuya firma y fecha de expiración son
    # válidas; None en caso contrario (token falsificado, expirado o ilegible)
    def check(self, token: str) -> dict | None:
        try:
            return jwt.decode(token, self._secret, algorithms=["HS256"])
        except jwt.InvalidTokenError:
            return None


def auth_service() -> AuthService:
    return current_app.extensions["auth"]
    • líneas 24–31: verificación de un nombre de usuario y una contraseña. [bcrypt.checkpw] calcula el hash de la contraseña ingresada con el salt del hash almacenado y compara ambos hashes. Un nombre de usuario desconocido y una contraseña incorrecta dan el mismo resultado, [None];
    • líneas 34–44: generación del token. Su contenido es un diccionario de afirmaciones (claims) sobre el usuario. Algunas tienen nombres estandarizados: [sub] (*subject*), el identificador del usuario; [iat] (*issued at*), la fecha de creación; [exp] (*expiration*), la fecha de expiración. Las demás son arbitrarias: en este caso, el nombre y el rol. [jwt.encode] genera el token y lo firma con el algoritmo [HS256] (HMAC-SHA256, una firma con una clave secreta compartida). Las fechas deben ser fechas con zona horaria: [datetime.now(timezone.utc)];
    • líneas 48–30: verificación del token. [jwt.decode] verifica la firma y la fecha de expiración, y luego devuelve las afirmaciones. Cualquier anomalía (token falsificado, expirado o mal formado) lanza una excepción de la familia [InvalidTokenError]. El parámetro [algorithms] especifica los algoritmos aceptados: sin él, un atacante podría crear un token que declare un algoritmo distinto (o incluso ninguno, [none]).

    # auth/security.py: el usuario de cada solicitud, y la protección de las acciones
from functools import wraps

from flask import g, redirect, request, url_for

from auth.service import COOKIE, auth_service


def register(app):

    # antes de cada acción: el token de la cookie -> g.user (sus claims), o None
    @app.before_request
    def read_token():
        token = request.cookies.get(COOKIE)
        g.user = auth_service().check(token) if token else None


# un decorador: la acción se ejecuta solo para un usuario autenticado;
# de lo contrario, se redirige a la página de inicio de sesión
def login_required(action):
    @wraps(action)
    def protected_action(*args, **kwargs):
        if g.user is None:
            response = redirect(url_for("auth.form"))
            # una cookie presente pero inválida (token expirado, falsificado): la eliminamos
            if COOKIE in request.cookies:
                response.delete_cookie(COOKIE)
            return response
        return action(*args, **kwargs)

    return protected_action
    • líneas 13–15: antes de cada acción, se verifica el token de la cookie; [g.user] contiene las afirmaciones de un token válido, o [None]. Esta función no rechaza nada: establece quién es el usuario. Esto es la autenticación;
    • líneas 20–31: el decorador que exige un usuario autenticado. Para un visitante anónimo, no devuelve la acción, sino que redirige a la página de inicio de sesión. Si el navegador envió una cookie, significa que el token no es válido (expirado o falsificado): aprovechamos para eliminarla ([delete_cookie] envía una cookie vacía que ya expiró).

    # controllers/auth.py: inicio y cierre de sesión
from flask import Blueprint, redirect, render_template, request, url_for

from auth.service import COOKIE, auth_service

auth = Blueprint("auth", __name__)


@auth.get("/")
def home():
    return redirect(url_for("profile.display"))


@auth.get("/login")
def form():
    return render_template("auth/login.html")


@auth.post("/login")
def login():
    login = request.form.get("login")
    user = auth_service().validate(login, request.form.get("password"))
    if user is None:
        # un mensaje deliberadamente vago: no indicamos si es el login o la contraseña
        return render_template("auth/login.html", login=login,
                               error="Incorrect login or password.")
    response = redirect(url_for("profile.display"))
    # el token, en una cookie: el JavaScript de la página no puede leerlo
    # (httponly); no acompaña a las solicitudes POST provenientes de otros sitios
    # (samesite); desaparece al mismo tiempo que expira el token (max_age)
    response.set_cookie(COOKIE, auth_service().create_token(user), httponly=True,
                        samesite="Lax", max_age=auth_service().duration)
    return response


# cierre de sesión: solo POST (un simple enlace, colocado en otro sitio, no puede
# cerrar la sesión del usuario sin que lo sepa); eliminamos la cookie
@auth.post("/logout")
def logout():
    response = redirect(url_for("auth.form"))
    response.delete_cookie(COOKIE)
    return response
    • líneas 20–26: el inicio de sesión. Si falla, el formulario se vuelve a mostrar con el nombre de usuario ingresado y un mensaje deliberadamente vago: decir “nombre de usuario desconocido” le revelaría a un atacante qué nombres de usuario existen;
    • líneas 27–32: si tiene éxito, el token se almacena en una cookie, con una redirección a la página protegida (esquema PRG). La cookie es [httponly]: el [JavaScript] de la página no puede leerla, lo que protege el token contra la inyección de scripts (XSS); es [samesite="Lax"]: el navegador no la envía con una solicitud POST originada en otro sitio, lo que protege la aplicación contra los ataques CSRF (ejemplo 18); su duración ([max_age], que acepta un [timedelta]) es la del token. En producción, con HTTPS, agregaríamos [secure=True]: la cookie nunca se enviaría por una conexión no cifrada;
    • líneas 38–41: cerrar sesión elimina la cookie. Es una acción POST: un simple enlace a [/logout], colocado en otro sitio o dentro de una imagen, no puede cerrar la sesión del usuario sin que este lo sepa. Cabe señalar una limitación de los tokens: el token en sí sigue siendo válido hasta que expira. Alguien que haya hecho una copia podría seguir usándolo. Por eso su vida útil es limitada.

from functools import wraps

from flask import abort, g, redirect, request, url_for

from auth.service import COOKIE, auth_service


def register(app):

    # antes de cada acción: el token de la cookie -> g.user (sus claims), o None
    @app.before_request
    def read_token():
        token = request.cookies.get(COOKIE)
        g.user = auth_service().check(token) if token else None


# un decorador: la acción se ejecuta solo para un usuario autenticado;
# de lo contrario, se redirige a la página de inicio de sesión
def login_required(action):
    @wraps(action)
    def protected_action(*args, **kwargs):
        if g.user is None:
            response = redirect(url_for("auth.form"))
            # una cookie presente pero inválida (token expirado, falsificado): la eliminamos
            if COOKIE in request.cookies:
                response.delete_cookie(COOKIE)
            return response
        return action(*args, **kwargs)

    return protected_action


# un decorador CON UN PARÁMETRO: @role_required("ADMIN"). role_required("ADMIN") devuelve
# el decorador propiamente dicho, que recibe la acción. Se usa DESPUÉS (debajo) de
# @login_required: el usuario está entonces necesariamente autenticado
def role_required(role: str):
    def decorator(action):
        @wraps(action)
        def protected_action(*args, **kwargs):
            if g.user["role"] != role:
                abort(403)  # acceso denegado
            return action(*args, **kwargs)

        return protected_action

    return decorator
    • líneas 37–47: [@role_required("ADMIN")] tiene un parámetro. La expresión que sigue a [@] se evalúa primero: [role_required("ADMIN")] devuelve una función, [decorator], que es el decorador propiamente dicho, aplicado a la acción. Tenemos, por lo tanto, tres funciones anidadas: [role_required] recibe el rol, [decorator] recibe la acción y [protected_action] recibe los parámetros de la solicitud y realiza el trabajo. Cada una tiene acceso a las variables de las funciones que la contienen ([role], [action]);
    • línea 42: un usuario autenticado que no tiene el rol solicitado recibe un error 403 (*Forbidden*). Esto es muy distinto de lo que sucede con un usuario anónimo, que es redirigido a la página de inicio de sesión: iniciar sesión no serviría de nada, ya que el usuario ya está autenticado.

def svg(text: str) -> str:
    parts = [f'<svg xmlns="http://www.w3.org/2000/svg" width="{WIDTH}" height="{HEIGHT}" '
             f'viewBox="0 0 {WIDTH} {HEIGHT}">',
             '<rect width="100%" height="100%" fill="#f5f7fa"/>']

    # los caracteres: cada uno ampliado, inclinado, desplazado, y cada punto
    # movido ligeramente al azar
    step = (WIDTH - 20) / len(text)
    for i, character in enumerate(text):
        scale = random(4.6, 5.6)  # tamaño de una unidad de la cuadrícula, en píxeles
        angle = random(-0.35, 0.35)  # rotación, en radianes (aproximadamente ±20°)
        cx = 10 + step * (i + 0.5) + random(-3, 3)  # centro del carácter
        cy = HEIGHT / 2 + random(-4, 4)
        d = []
        for stroke in FONT[character]:
            for k in range(0, len(stroke), 2):
                # punto de la cuadrícula, centrado en (2, 3), distorsionado, rotado, colocado
                x = (stroke[k] - 2 + random(-0.2, 0.2)) * scale
                y = (stroke[k + 1] - 3 + random(-0.2, 0.2)) * scale
                px = cx + x * math.cos(angle) - y * math.sin(angle)
                py = cy + x * math.sin(angle) + y * math.cos(angle)
                d.append(f"{'M' if k == 0 else 'L'}{px:.1f} {py:.1f}")
        parts.append(f'<path d="{" ".join(d)}" fill="none" stroke="{color()}" '
                     f'stroke-width="{random(2.2, 3):.1f}" stroke-linecap="round" '
                     f'stroke-linejoin="round"/>')

    # 3 trazos de interferencia: curvas que cruzan la imagen
    for _ in range(3):
        parts.append(
            f'<path d="M{random(0, 20):.1f} {random(5, 45):.1f} '
            f'C{random(30, 60):.1f} {random(0, 50):.1f} {random(90, 120):.1f} {random(0, 50):.1f} '
            f'{random(130, 150):.1f} {random(5, 45):.1f}" fill="none" stroke="{color()}" '
            f'stroke-width="1.3"/>')
    parts.append("</svg>")
    return "".join(parts)

import secrets
from dataclasses import dataclass
from datetime import datetime, timedelta
from threading import Lock

from flask import current_app

from auth import captcha_drawing

LIFETIME = timedelta(minutes=10)


# un captcha: su identificador, y su imagen (SVG)
@dataclass(frozen=True)
class Captcha:
    id: str
    svg: str


class CaptchaService:

    def __init__(self):
        # identificador -> (respuesta esperada, fecha de expiración)
        self._pending: dict[str, tuple[str, datetime]] = {}
        self._lock = Lock()

    def generate(self) -> Captcha:
        text = captcha_drawing.random_text(5)
        id = secrets.token_urlsafe(16)  # un identificador aleatorio, imposible de adivinar
        with self._lock:
            self._pending[id] = (text, datetime.now() + LIFETIME)
        return Captcha(id, captcha_drawing.svg(text))

    # el captcha se CONSUME en todos los casos: una imagen se usa una sola vez
    def check(self, id: str | None, answer: str | None) -> bool:
        with self._lock:
            expected = self._pending.pop(id, None) if id else None
        if expected is None or answer is None:
            return False
        text, expires = expected
        return expires > datetime.now() and text.lower() == answer.strip().lower()


def captcha_service() -> CaptchaService:
    return current_app.extensions["captchas"]
    • líneas 28–33: un nuevo CAPTCHA: texto aleatorio, un identificador aleatorio e imposible de adivinar ([secrets.token_urlsafe]) y la imagen. Para cada identificador, el servidor almacena la respuesta esperada y una fecha de expiración. La página recibe solo el identificador y la imagen: la respuesta nunca sale del servidor;
    • líneas 36–42: verificación. [pop] elimina la entrada del diccionario y la devuelve: el CAPTCHA se consume en todos los casos, tenga éxito o no la verificación. Sin esto, un programa podría probar todas las respuestas posibles sobre la misma imagen. La comparación ignora las mayúsculas y los espacios alrededor de lo escrito.

    Este servicio conserva datos en memoria en el servidor: es una desviación del principio de servidor sin estado (véase el capítulo sobre los ámbitos), aceptable para datos de corta duración. Con varios servidores, los datos tendrían que almacenarse en un sistema de almacenamiento compartido (una base de datos, [Redis]...). Observe también que los CAPTCHA que nunca se han utilizado no se eliminan: el caso de estudio limpia periódicamente los CAPTCHA vencidos.

import math
from datetime import datetime, timedelta
from threading import Lock

from flask import current_app

MAX_FAILURES = 3
BLOCK_DURATION = timedelta(minutes=1)


class Counter:
    def __init__(self):
        self.failures = 0
        self.blocked_until = datetime.min


class LimiterService:

    def __init__(self):
        self._counters: dict[str, Counter] = {}
        # varias solicitudes simultáneas, un solo acceso a la vez
        self._lock = Lock()

    # el número de segundos de bloqueo restantes (0: no bloqueado)
    def blocked_seconds(self, ip: str) -> int:
        with self._lock:
            counter = self._counters.get(ip)
            if counter is None:
                return 0
            remaining = (counter.blocked_until - datetime.now()).total_seconds()
            return max(0, math.ceil(remaining))

    def failure(self, ip: str):
        with self._lock:
            counter = self._counters.setdefault(ip, Counter())
            counter.failures += 1
            if counter.failures >= MAX_FAILURES:
                counter.blocked_until = datetime.now() + BLOCK_DURATION
                counter.failures = 0  # después del bloqueo, se empieza de nuevo desde cero

    def success(self, ip: str):
        with self._lock:
            self._counters.pop(ip, None)


def limiter_service() -> LimiterService:
    return current_app.extensions["limiter"]
    • líneas 12–15: para cada dirección IP, un número de intentos fallidos y una fecha de fin de bloqueo ([datetime.min], la fecha más antigua posible, significa «no bloqueada»);
    • líneas 26–32: el número de segundos que faltan para que termine el bloqueo, redondeado hacia arriba al entero más próximo ([math.ceil]);
    • líneas 34–40: un fallo más. [setdefault] obtiene el contador de la dirección, creándolo si no existe. En el tercer fallo, la dirección se bloquea durante un minuto y el contador se reinicia a cero;
    • líneas 42–44: una conexión exitosa borra el contador.

    # controllers/auth.py: inicio de sesión (con captcha y límite de intentos) y cierre de sesión
from flask import Blueprint, redirect, render_template, request, url_for

from auth.captcha import captcha_service
from auth.limiter import limiter_service
from auth.service import COOKIE, auth_service

auth = Blueprint("auth", __name__)


@auth.get("/")
def home():
    return redirect(url_for("profile.display"))


@auth.get("/login")
def form():
    return login_page()


@auth.post("/login")
def login():
    login = request.form.get("login")
    # la dirección IP del cliente
    ip = request.remote_addr

    # 1. una dirección bloqueada ni siquiera es atendida
    seconds = limiter_service().blocked_seconds(ip)
    if seconds > 0:
        return login_page(login, f"Too many attempts: try again in {seconds} s.")
    # 2. primero el captcha (barato), después la contraseña (bcrypt, costoso)
    if not captcha_service().check(request.form.get("captchaId"), request.form.get("captcha")):
        limiter_service().failure(ip)
        return login_page(login, "The image code is incorrect.")
    user = auth_service().validate(login, request.form.get("password"))
    if user is None:
        limiter_service().failure(ip)
        return login_page(login, "Incorrect login or password.")
    limiter_service().success(ip)
    response = redirect(url_for("profile.display"))
    response.set_cookie(COOKIE, auth_service().create_token(user), httponly=True,
                        samesite="Lax", max_age=auth_service().duration)
    return response


@auth.post("/logout")
def logout():
    response = redirect(url_for("auth.form"))
    response.delete_cookie(COOKIE)
    return response


# cada vez que se muestra el formulario se construye un captcha NUEVO
def login_page(login: str | None = None, error: str | None = None):
    return render_template("auth/login.html", login=login, error=error,
                           captcha=captcha_service().generate())
    • línea 25: la dirección del cliente, IP;
    • líneas 28–30: una dirección bloqueada ni siquiera es atendida;
    • líneas 32–34: el CAPTCHA se verifica antes que la contraseña: verificarlo casi no cuesta nada, mientras que [bcrypt] es lento a propósito. Un programa que introduzca un CAPTCHA incorrecto no provocaría, por tanto, la ejecución de [bcrypt]. Todo fallo, ya sea del CAPTCHA o de la contraseña, se contabiliza;
    • línea 39: un inicio de sesión exitoso borra el contador de fallos;
    • líneas 54–56: cada vez que se muestra el formulario, se genera un nuevo CAPTCHA, incluso después de un fallo.
